# Дизайн-система Aurora

Дата: 2026-09-08
Статус: согласован, готов к передаче дизайнеру

## 1. Зачем

Приложение мониторинга автопарка переезжает на Flutter, чтобы Android и iOS
выпускались одновременно. Вместе с переездом нужен редизайн и внятная
white-label архитектура: Aurora — базовый бренд, поверх него строятся МТС,
Irissoft и следующие.

Документ описывает дизайн-систему: токены, палитру, типографику, форму,
поведение и состав компонентов. Он адресован дизайнеру, который будет рисовать
Figma-библиотеку, и разработчику, который будет её кодировать.

### Что не входит

- Редизайн конкретных экранов — отдельный цикл после Figma-библиотеки.
- План миграции Kotlin → Flutter — отдельный цикл.
- Информационная архитектура и навигация — не меняются этим документом.

## 2. Исходное состояние

| Что | Сейчас |
|---|---|
| UI | 76 XML-layout, View-система, Compose нет |
| Код | ~23 400 строк Kotlin, логика внутри фрагментов |
| Бренды | три source set: `aurora`, `irissoft`, `mts` |
| Дублирование | `MapFragment` (~1 480 строк) скопирован в каждый флейвор; между `aurora` и `mts` разница 29 строк diff |
| Реальные различия брендов | base URL, дефолтная локаль, набор цветов |
| Тёмная тема | отсутствует: `values-night/` содержит один неиспользуемый overlay |
| Токены | нет; в layout стоят `@color/colorWhite`, `@color/colorBlack` напрямую |
| Иконки | 23 из 206 drawable имеют цвет в имени файла (`ic_map_blue`, `ic_close_white`) |
| Вордмарк | `branded_image.xml` залит `#FF000000` без возможности тонирования |
| Языки | 14, включая арабский (RTL) и греческий |

Ключевая находка: палитра логотипа и палитра приложения не совпадают. В
`aurora_logo_240.xml` живут `#0081C9`, `#004F9F`, `#1E2668`, `#F4E84B`, а
интерфейс покрашен в `#3493F8` — цвет, которого в знаке нет.

## 3. Принятые решения

| Решение | Выбор | Почему |
|---|---|---|
| Платформа | Flutter | Переиспользуемой логики в текущем коде почти нет (`TrackerViewModel` сросся с `MapLibreMap`, `GoogleMap`, `Context`); приложение упирается в четыре нативные интеграции — карта, плеер, графики, PDF — и на Flutter у каждой одна поддерживаемая реализация вместо двух собственных `expect/actual` |
| Где живёт индивидуальность | В форме и поведении, не в цвете | Бренды заменяют палитру целиком (МТС уже ушёл в серый + красный). Характер, привязанный к цвету, не пережил бы перекраску |
| Хроматика интерфейса | Обвязка нейтральная, цвет только у данных | Приложение картоцентричное: чем тише хром, тем читаемее карта и отчёты |
| Нейтрали | Подкрашены в оттенок бренда (`neutralHue`) | Одна переменная отличает холодную Aurora от тёплого МТС; стоит ноль усилий, даёт всю разницу настроения |
| Брендовый цвет | Из логотипа: `#0066B8` / `#3E9BE0` | У знака уже есть характер, приложение им не пользовалось |
| Жёлтый `#F4E84B` | Не используется | Рассматривался как маркер фокуса, отклонён |
| Форма | Панельная: радиусы 8/12/16, строка 52, **теней нет** | Плотность инструмента при современном виде; разделение тоном работает одинаково в обеих темах, дёшево на длинных списках и переживает перекраску |
| Шрифт | Inter везде, обе платформы | Единый вид на iOS и Android — ради этого и затевалась кроссплатформа |
| Моноширинный | Нет | Выравнивание колонок даёт `tabular-nums` внутри Inter; отдельная гарнитура была излишеством |
| Статусные цвета | Общие для всех брендов | Означают состояние объекта, а не клиента |

## 4. Архитектура токенов

Три слоя. Компонент видит только средний.

### 4.1 Primitive

Сырые значения без смысла: `neutral.400`, `brand.600`, `space.4`, `radius.md`.
Не пишутся руками — генерируются:

- нейтральная шкала — из `neutralHue` и фиксированной кривой светлоты;
- брендовая шкала — из `brand.seed`.

Поэтому новый бренд не требует подбирать десяток оттенков вручную.

### 4.2 Semantic

Привязка к роли и к теме. Только этот слой имеет светлый и тёмный вариант, и
только его видят компоненты.

### 4.3 Component

Точечно, где нужна отдельная ручка: `listRow.height`, `chip.radius`,
`button.primary.bg`. Не заводится «на всякий случай».

### 4.4 Правило

**Компонент никогда не обращается к primitive напрямую.** Встретившийся в
виджете `neutral900` — это баг. Именно так тёмная тема ломается в текущем
приложении: `@color/colorWhite` стоит прямо в layout, и никакой `values-night`
его не переопределит.

|---|---|

для светлой и тёмной темы.

## 6. Типографика

Inter, все начертания. Арабский — Noto Sans Arabic (у Inter арабского нет).

| Роль | Размер / интерлиньяж | Вес | Трекинг | Где |
|---|---|---|---|---|
| `display` | 28 / 34 | 600 | −1.5% | заголовок экрана |
| `title` | 20 / 26 | 600 | −1% | заголовок секции, диалога |
| `section` | 15 / 20 | 600 | 0 | подзаголовок внутри контента |
| `body` | 15 / 22 | 400 | 0 | основной текст |
| `label` | 13 / 18 | 550 | 0 | строка списка, кнопка |
| `caption` | 11 / 15 | 400 | 0 | вторичное, единицы измерения |
| `overline` | 9 / 12 | 700 | +8%, uppercase | липкий заголовок даты |
| `number.lg` | 20 / 24 | 600 | `tnum` | скорость в HUD |
| `number.md` | 14 / 18 | 600 | `tnum` | число в строке отчёта |
| `number.sm` | 11 / 14 | 600 | `tnum` | время, координаты |

Числовые роли — тот же Inter с включёнными табличными цифрами
(`font-variant-numeric: tabular-nums`), а не отдельная гарнитура.

**Правило:** любое число в колонке набирается числовой ролью. Проприетарные
`LowercasedTextView` (46 использований) и `DistanceTextView` (14) перестают
быть виджетами — это правила форматирования, им место в типографике и
форматтерах.

## 7. Пространство и форма

**Отступы**, шаг 4: `2, 4, 8, 12, 16, 20, 24, 32, 40, 48`.
Горизонтальный отступ экрана — 16, внутренний отступ строки — 14.

**Радиусы:** `4` (вложенное), `8` (чип, поле ввода, кнопка), `12` (панель),
`16` (экран, шторка), `pill` (аватар, счётчик).

**Высоты строк:** `40` компактная, `52` основная, `64` двухстрочная.
Минимальная зона нажатия — `44` независимо от визуального размера.

**Разделение поверхностей — тоном и волосяной границей. Теней нет.**
`elevation` в системе не существует как понятие: нет `boxShadow`, нет
`Material.elevation`, нет ripple с тенью. Это осознанный характерный приём —
он одинаково работает в обеих темах (в тёмной тени всё равно не читаются),
дёшев на длинных списках и целиком переживает перекраску.

**Выделение активного:** вертикальная полоса 2 dp слева цветом
`action.primary` плюс `surface.selected`. Один выделитель на экране — не
подсвечиваем одновременно фоном, полосой и рамкой.

## 8. Поведение

| Токен | Значение |
|---|---|
| `duration.fast` | 120 мс |
| `duration.base` | 200 мс |
| `duration.slow` | 320 мс |
| `duration.dataInterp` | 500 мс |
| `curve.enter` | `easeOutCubic` |
| `curve.exit` | `easeInCubic` |

**Правила:**

1. **Движение объясняет, откуда взялся экран.** Панель выезжает с той
   стороны, где живёт: детали трека — справа, фильтр — снизу, детали
   уведомления — из строки списка. `duration.base`, `curve.enter`.
2. **Данные не мигают.** Объект на карте интерполирует позицию за
   `duration.dataInterp`, а не телепортируется. Числа в HUD меняются коротким
   кроссфейдом. Мигающий интерфейс читается как глючащий.
3. **Скелетоны вместо спиннеров** там, где форма результата известна заранее
   (списки, отчёты). Спиннер остаётся для построения трека и загрузки видео.
4. **RTL с первого дня.** Арабский уже в проекте. Все отступы логические
   (`start`/`end`). Карта, графики и числа не зеркалятся; стрелки направления
   движения — зеркалятся.

## 9. Компоненты

### 9.1 Базовые

| Компонент | Варианты | Заменяет |
|---|---|---|
| `Text` | 10 типографических ролей | 404 `TextView`, 46 `LowercasedTextView`, 14 `DistanceTextView` |
| `Button` | primary, secondary, ghost, danger, icon, FAB | 31 `Button`, 9 `ImageButton`, 3 `FloatingActionButton` |
| `TextField` | text, password, search, numeric | 42 `EditText` |
| `Checkbox` | — | 16 `CheckBox` |
| `Switch` | — | 6 `Switch` / `SwitchCompat` |
| `Select` | bottom-sheet picker, одиночный и множественный | 9 `Spinner` |
| `Chip` | filter, choice, counter | ручные drawable (`filter_button_back.xml`) |
| `Progress` | linear, circular, **skeleton** | 17 `ProgressBar` |

`Spinner` заменяется на bottom-sheet picker: выпадающие списки плохо работают
на мобильном, особенно при выборе из сотни объектов.

### 9.2 Доменные

Их нет ни в одной готовой библиотеке — дизайнер рисует их первыми.

| Компонент | Что делает |
|---|---|
| `ObjectRow` | строка объекта: статус, номер, водитель, метрика. 15 существующих адаптеров сводятся к 3–4 вариантам |
| `MetricCell` | число + единица, выравнивание вправо, табличные цифры |
| `StatusDot` / `StatusBadge` | пять состояний из §5.3 |
| `MapHUD` | панель показаний над картой |
| `MapMarker` | объект, кластер, стоянка, выбранный — вместо 10+ отдельных drawable `map_track_*` |
| `TrackPolyline` | обычный, превышение скорости, выбранный |
| `DateRangeBar` | период + быстрые пресеты (в коде уже есть `PredifinedTimePeriods`) |
| `ReportSection` | липкий заголовок + строки + итог |
| `Chart` | обёртка над `fl_chart` с токенами; заменяет 3 `LineChart` |
| `PlayerChrome` | 2 плеера + `custom_player_control.xml` |
| `EmptyState` / `ErrorState` | **сейчас отсутствуют полностью** |

Пустые состояния и состояния ошибки — самая частая дыра при редизайне: экран
без данных выглядит как сломанный.

### 9.3 Иконки

Один набор, сетка 24, обводка 1.5, тонируется токеном `text.*` или
`action.*`. 23 иконки с цветом в имени файла (`ic_map_blue`, `ic_close_white`,
`ic_eye_white`) схлопываются в 23 обычные. Вордмарк `branded_image.xml`
перестаёт быть залитым `#FF000000` и принимает `currentColor`.

## 10. Брендирование

Бренд — один файл конфигурации:

```json
{
  "id": "aurora",
  "brand": { "seed": "#0066B8", "neutralHue": 232 },
  "logo": "aurora.svg",
  "wordmark": "aurora-wordmark.svg",
  "appName": "Aurora",
  "baseUrl": "https://api.aurora-soft.by/",
  "defaultLocale": "en"
}
```

Меняются ровно четыре визуальные переменные: `brand.seed`, `neutralHue`,
`logo`, `wordmark`. Не меняется ничего из: радиусов, отступов, высот строк,
шрифта, статусных цветов, правил движения, отсутствия теней.

Это заменяет 4 900 строк дублированного Kotlin в трёх source set, которые
существуют сейчас ради base URL, дефолтной локали и набора цветов.

**Новый бренд подключается добавлением файла и ассетов, без строк кода.**

## 11. Поставка

**Источник истины — JSON токенов в репозитории** (Style Dictionary / W3C
Design Tokens). Из него генерируются:

- Dart: `AuroraTheme extends ThemeExtension<AuroraTheme>` с полями
  семантического слоя; бренд выбирается флейвором, светлая и тёмная — две
  инстанции того же класса;
- Figma Variables: три коллекции (primitive / semantic / component) с модами
  `brand × theme` — четыре комбинации переключаются одним селектором.

**Направление синхронизации: JSON → Figma, не наоборот.** Если дизайнер правит
цвета в Figma напрямую, через месяц вернутся три расходящихся `colors.xml` в
новой обёртке.

Figma-файл содержит: переменные, компоненты с вариантами, и эталонные экраны —
по одному на раздел (карта, автопарк, отчёт, уведомления, видео, настройки) в
светлой и тёмной теме; для МТС — карта и отчёт, для проверки перекраски.

## 12. Что проверить перед стартом

- **Покрытие глифов Inter** для белорусского, украинского и греческого на
  реальных строках из `values-be`, `values-uk`, `values-el`. Проверка не
  проводилась.
- **Noto Sans Arabic** рядом с Inter: совпадение оптического размера и высоты
  строки в смешанной вёрстке.
- **Контраст** всех пар `text.*` / `surface.*` в обеих темах и обоих брендах
  по WCAG AA (4.5:1 для текста, 3:1 для крупного). Проверять генератором, а
  не на глаз — шкалы генерируемые, ошибка попадёт сразу во все бренды.
- **Читаемость `map.track.*` на спутниковой подложке.** Синий трек на
  спутнике тонет — возможно, для спутникового режима нужен отдельный
  токен-переопределение.
- **Тёплые нейтрали МТС** (hue 28°) против их фирменного красного: тёплый
  серый рядом с красным может уходить в розовый.

## 13. Порядок работ

1. Файл токенов + генераторы Dart и Figma.
2. Figma: переменные, базовые компоненты (§9.1).
3. Figma: доменные компоненты (§9.2) — самая содержательная часть.
4. Эталонные экраны, светлая и тёмная.
5. Проверка перекраски на МТС.
6. Реализация пакета `aurora_design_system` во Flutter.

Редизайн экранов и миграция начинаются после пункта 4 и планируются отдельно.
